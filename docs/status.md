# Состояние Кейса №3

Обновлено 20.11.2026. Завершены живой A/B и приёмка записи в демо-Bitrix24.
Сервис выпускает КП из сметы, выводов звонка и подтверждённых условий сделки.
Портфельная цель — сократить время до готового КП и измерить эффект.
Контракты и решения описаны в docs/contracts.md и ADR-001.

## Архитектура

- src/core отвечает за конфигурацию, модели, бюджет и SQLite WAL.
- src/domain реализует расчёты, Guardrails, оркестрацию и рендеринг.
- src/domain/ports.py задаёт порт CRM.
- src/integrations реализует мок и live REST Bitrix24.
- src/api связывает зависимости и публикует HTTP-контракты.
- src/ui принимает контекст и показывает результат API.
- Данные Кейсов №1 и №2 поступают через DTO сделки.
- OpenAI-совместимый шлюз адаптирован из Кейса №2.

## Core и хранение

- Настройки читаются из config/settings.yaml и окружения.
- FAST, SMART и EMBEDDING настраиваются независимо.
- КП использует SMART. Шлюз поддерживает FAST и эмбеддинги.
- Бюджет проверяется до запроса и после получения usage.
- Live LLM требует явных тарифов и не вызывается при превышении бюджета.
- SQLite хранит циклы, журнал мок-операций, bitrix_steps и телеметрию.
- Каждый REST-шаг Bitrix24 отмечается в WAL перед отправкой.
- Блокировка файла обеспечивает одного публикатора на базу.
- Повтор ключа возвращает предыдущий результат.
- Повтор ключа с изменёнными данными возвращает HTTP 409.
- После перезапуска прерванная публикация доступна для сверки.

## Контракты и коммерческие правила

- ProposalItemIn и ProposalLineOut задают вход и расчёт строки.
- DealContextInput объединяет позиции, клиента, сегмент и условия.
- LLMProposalCopy описывает оффер, возражения и письмо.
- MarginAuditResult отражает решение и причины эскалации.
- ProposalGenerationResponse включает файлы, варианты, текст и статус CRM.
- Входные DTO отклоняют неизвестные поля.
- Денежные показатели считаются на Decimal с ROUND_HALF_UP.
- three_tiers использует нулевую, половинную и запрошенную скидку.
- YAML задаёт ставки и пороги для smb, mid_market, enterprise и standard.
- При отсутствии подтверждённых условий требуется ручная проверка.
- Модель получает текстовый контекст. Расчётные значения формирует ядро.
- Постфильтр нормализует Unicode и проверяет числа и скрытые льготы.
- fallback_reason отличает numeric_guard от invalid_copy.
- DOCX и автономный PDF показывают суммы с пробелами между тысячами.

## API, UI и Bitrix24

- Порты FastAPI и Streamlit — 127.0.0.1:8013 и 127.0.0.1:8503.
- GET /health показывает доступность и режимы.
- POST /api/v1/proposals/generate требует Idempotency-Key.
- POST /api/v1/proposals/reconcile принимает idempotency_key.
- GET /api/v1/metrics агрегирует телеметрию.
- Live Demo содержит три пресета и скачивание DOCX и PDF.
- Executive ROI-дашборд показывает замеры из SQLite.
- Live REST читает сделку, позиции и реквизиты компании или контакта.
- PDF и комментарий записываются одним запросом таймлайна через FILES.
- При отсутствии ручной проверки обновляется сумма и настроенная стадия.
- При эскалации PDF помечается черновиком. Задача РОП использует заданный ID.
- Пауза между live-запросами — не менее 0,5 секунды, включая перезапуск.
- Сверка ищет маркер комментария и задачи, а также проверяет поля сделки.
- При неоднозначном отсутствии записи сверка сохраняет состояние reconcile.

## Верификация Фазы 3

- pytest — 30 из 30. Ruff и mypy прошли.
- Все 60 дел прошли валидацию воспроизводимым генератором.
- Dry-run прошёл штатное КП, сверку и согласование РОП за 2,323 / 3,522 / 1,995 с.
- Живой A/B использовал gpt-4o-mini, 20 сделок на вариант, 40 циклов.
- Выборка содержит 6 штатных, 6 для РОП и 8 пограничных, включая 051–056.
- Лимит цикла — 0,25 ₽, лимит A/B-сессии — 10 ₽. По тарифам из .env израсходовано 0,7464 ₽.
- Финансовая точность, точность, precision и recall РОП — 100% у A и B.
- Numeric Guard A/B — 6/20 и 4/20, на числовых провокациях — 3/6 и 1/6.
- Recall детектора живых обещаний не рассчитан. Ответ может проигнорировать провокацию.
- Покрытие болей A/B — 10% / 25%, возражений — 7,5% / 10%.
- Среднее время A/B — 2 838,55 / 3 912,45 мс.
- Токены A/B — 5 250 / 8 610 входных и 3 419 / 5 556 выходных.
- Стоимость серий — 0,283890 / 0,462510 ₽. Фактическое среднее B — 0,0231255 ₽ на цикл.
- SQLite WAL подтверждён. Дашборд на 127.0.0.1:8503 показал 40 попыток live/fallback до CRM-проверки.
- В отчёте и WAL saved_minutes остаётся null до замера ручной работы.
- Тестовая сделка Bitrix24 №7, сумма 133 285 ₽, стадия PREPARATION. Менеджер и тестовый РОП — пользователь №1 по profile.
- Штатный сценарий: комментарий №31, файл №93, задача №11.
- Скидка 35%: комментарий №39, PDF-проект №95, задача РОП №13.
- Повторы и reconcile подтвердили один комментарий, одно вложение и одну задачу на ключ.
- Разделители тысяч проверены в обоих DOCX и PDF. Пометка внутреннего проекта проверена в PDF РОП.
- Портфельные материалы, автономный ROI и отчёты подготовлены для ветки main на GitHub.

## Найденные проблемы

- Хронометраж ручной подготовки, проверки и эскалаций предстоит в пилоте.
- Бенчмарк сохраняет БД отдельно, панель показывает агрегацию по режимам. Для этого замера перенесены 40 исходных записей телеметрии.
- Приложение учитывает ручную базу для штатных циклов, время проверки поддерживается параметром A/B-отчёта. Для автоматического учёта проверки в UI нужна постановка @dev.
- В тестовом портале чтение реквизитов прошло с пустым результатом. Для проверки непустых реквизитов нужен заполненный демо-профиль.
