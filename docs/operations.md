# Локальная эксплуатация

Установите зависимости и запустите API и UI по [README](../README.md).
Выполните проверку портов и e2e в отдельном терминале:

```powershell
Invoke-RestMethod http://127.0.0.1:8013/health
Invoke-WebRequest http://127.0.0.1:8503/_stcore/health
.venv/Scripts/python -m ops.runners.smoke --dry-run
.venv/Scripts/python -m pytest
.venv/Scripts/python -m ruff check .
.venv/Scripts/python -m mypy .
```

Сквозной прогон создаёт три синтетические сделки в мок-журнале и инициирует
сверку после потери ответа. Храните один экземпляр API на одну SQLite-базу.
При восстановлении зависшего цикла перезапустите API и вызовите reconcile,
если клиент получил состояние reconcile. После сбоя до подготовки документов
повторите генерацию с исходным ключом и контекстом.

Для Ollama задайте LLM_MODE=live, BASE_URL=http://127.0.0.1:11434/v1,
SMART_LLM_MODEL с установленной моделью и явные тарифы в рублях за миллион
токенов. Для локальной модели допустимо задать нулевые тарифы. Запустите
API без --mock-llm и вызовите раннер с --live-llm на синтетических данных.
Провайдер должен возвращать usage и поддерживать режим json_object.

Установите PDF_FONT только если системный шрифт не подходит. Команда
python -m scripts.create_default_template создаёт шаблон при его отсутствии.

## Live Bitrix24

Задайте BITRIX_MODE=live, HTTPS BITRIX_WEBHOOK_URL с правами CRM и задач,
BITRIX_DIRECTOR_ID и при необходимости BITRIX_PROPOSAL_STAGE. У webhook-пользователя
должны быть права на чтение сделки, реквизитов, комментариев и созданных задач.
Если код стадии отсутствует, адаптер обновляет только сумму сделки.
Черновики для ручной проверки прикрепляются к карточке и ставят задачу.
Операции для live выполняйте на отдельной тестовой сделке.

При состоянии reconcile вызовите POST /api/v1/proposals/reconcile с исходным ключом.
Подтверждённые шаги пропускаются. Комментарии и задачи на портале сверяются по
маркеру в тексте и заголовке, а сумма и стадия — чтением сделки.
Когда запись могла произойти, а проверка её не находит, цикл ждёт сверки.
Устраните недостаточные права и проверьте состояние на портале. Если результат
доказан, повторите сверку. Если портал подтверждает отсутствие записи, оператор
может вручную завершить конкретный шаг с исходным маркером и повторить сверку.
Исходный ключ, режим и портал должны совпадать с журналом.
Выдерживайте один экземпляр live-адаптера на портал, чтобы лимит действовал
для всего потока сервиса.

## Фаза 3. Живой A/B на стратифицированной подвыборке

Настройте SMART и тарифы в локальном `.env`. Для 40 циклов с потолком
10 ₽ установите `MAX_CYCLE_COST_RUB=0.25`. Из корня проекта выполните:

```powershell
.venv/Scripts/python -m ops.runners.phase3_ab --live-llm --session-budget-rub 10
```

Раннер сохраняет отдельные WAL-базы под `data/phase3-ab-*` и пишет
[живой отчёт](../artifacts/benchmarks/phase3_live_llm_report.json).
Он проверяет сумму лимитов до запуска и сверяет стоимость и токены с SQLite.
При наличии хронометража передайте оба параметра
`--manual-baseline-minutes` и `--automated-review-minutes`.
Executive ROI отображает основную БД. Для прогона Фазы 3 в неё перенесены
40 исходных строк телеметрии по уникальному `request_id`.
[Отчёт Bitrix24](../artifacts/benchmarks/phase3_bitrix24_report.json) хранит
результаты независимого чтения сделки, комментариев и задач после повторов.
